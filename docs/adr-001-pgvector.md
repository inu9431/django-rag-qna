# ADR-001: 벡터 검색 엔진으로 pgvector 선택

- **날짜**: 2026-05-21
- **상태**: 채택 (Accepted)

---

## 배경

기존 Django 봇 프로젝트는 PostgreSQL의 `pg_trgm` 익스텐션을 사용해 트라이그램 기반 텍스트 유사도 검색을 구현했습니다.
봇 응답 품질을 높이기 위해 의미(semantic) 기반 검색 도입을 검토했고, `pgvector`와의 성능·정확도 비교를 진행했습니다.

## 결정

PostgreSQL 익스텐션 `pgvector`를 채택하고, OpenAI `text-embedding-3-small` 모델로 임베딩을 생성합니다.

## 고려한 옵션

### Option 1: pg_trgm 유지

- **장점**
  - 외부 API 의존성 없음
  - 운영 비용 없음
  - 오타·부분 문자열 매칭에 강함
- **단점**
  - 의미 기반 유사도 파악 불가
  - 표현이 다른 동의어 질문 매칭 실패
  - 한국어 트라이그램 분리 효율 낮음

### Option 2: pgvector + OpenAI 임베딩 (채택)

- **장점**
  - 의미적으로 유사한 질문 정확히 매칭
  - 한국어·다국어 환경에서 강한 성능
  - 기존 PostgreSQL 인프라 재사용 가능 (별도 벡터 DB 불필요)
  - HNSW 인덱스로 대규모 데이터에서도 빠른 검색
- **단점**
  - OpenAI API 비용 발생 (임베딩 생성 시)
  - 외부 API 의존성 추가
  - 벡터 저장 용량 증가 (1536차원)

### Option 3: 별도 벡터 DB (Pinecone, Weaviate 등)

- **단점**
  - 별도 인프라 관리 필요
  - 비용 증가
  - 현재 규모에서 오버엔지니어링

## 결정 근거

1. **정확도 우선**: QnA 봇의 핵심 지표는 올바른 답변 매칭률입니다. pg_trgm은 "환불 어떻게 해요"와 "반품 절차 알려줘"처럼 표현이 다른 동의 질문을 매칭하지 못했습니다.

2. **인프라 단순화**: Pinecone 등 외부 벡터 DB 대신 기존 PostgreSQL에 pgvector 익스텐션만 추가해 운영 복잡도를 최소화합니다.

3. **확장성**: HNSW 인덱스는 데이터 증가 시에도 검색 성능을 유지합니다.

4. **비용 수용 가능**: 임베딩은 질문 저장 시 1회만 생성하므로 API 호출 비용이 제한적입니다.

## 트레이드오프 및 리스크

| 리스크 | 대응 방안 |
|--------|----------|
| OpenAI API 장애 | 임베딩은 저장 시 1회 생성 → 검색은 이미 저장된 벡터로 수행, 신규 저장만 영향받음 |
| API 비용 증가 | 동일 질문 중복 임베딩 방지 로직 추가 예정 |
| 벡터 용량 증가 | 정기적인 유사 중복 문서 정리 |

## 결과

기존 pg_trgm 대비 의미 기반 질문 매칭 정확도가 개선됐으며,
PostgreSQL 단일 인프라를 유지하면서 RAG 파이프라인을 구현했습니다.
